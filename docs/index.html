Before you start

What you’ll need

Setup takes a couple of minutes. Two things are required — the setup code and an address — and everything else can wait until later.

The setup code

It’s in the server’s log. Run docker logs ktl, or open the container’s log in Unraid or Portainer, and look for “setup code”. It stops strangers on your network from claiming the server.

The address people will use

For use away from home, put KTL behind a reverse proxy or a Cloudflare Tunnel and use that https:// address. For your own network only, http://<server>:8095 works.

Who you share with

Names and email addresses, up to six people including you. Each gets their own private space for pay and debts, and one-time sign-in links.

Optional extras

An email server so people can reset passwords themselves, a Firebase project for push notifications, and a Cloudflare Tunnel token. All can be added later from the admin page.

The setup

From docker run to a working household

The first run happens in the browser. Steps 3 to 5 are the same cards as the admin page, so anything you skip here can be done there later.

1

Deploy the container

You need Docker. Run the published image with a folder mounted at /data for the database, secrets, settings and backups.

docker run -d --name ktl --restart unless-stopped --stop-timeout 30 \
  -p 8095:3000 -v /path/to/ktl-data:/data ghcr.io/jpjoseph12/ktl:latest

Or use Compose — docker compose -f selfhost/docker-compose.yml up -d. On Unraid, go to Docker → Add Container, paste https://raw.githubusercontent.com/jpjoseph12/ktl/main/selfhost/unraid/ktl.xml as the template, or set Repository to ghcr.io/jpjoseph12/ktl:latest with port 3000 and a path for /data. Updates then come through Unraid’s own “check for updates”. Prefer to build it yourself? docker build -f selfhost/Dockerfile -t ktl:latest . from a clone of the repository.

2

Read the setup code

The server prints a code to its log when it starts. Five wrong tries at the setup page locks it for 15 minutes.

docker logs ktl 2>&1 | grep "setup code"
3

Open the setup page and claim the server

Go to http://<your-server>:8095/setup. One step creates the household and your own account at the same time, so a half-set-up server can’t exist: the setup code, the address, your household name, and your name, email and password. You become the household’s owner — the person who looks after the server.

4

Add the people you share with

Each person gets a one-time link: they open it, choose a password, and they’re in. No email server is needed for this. You can add or remove people later from the admin page, linked from House → Server.

5

Optional extras

Turn on sign-ups, add an email server, set up push notifications, or paste a Cloudflare Tunnel token. Skip any of these — they’re all on the admin page later.

6

Give people the address

On the Android app, the first launch asks for your server’s address; afterwards House → Server shows it. On a computer or tablet, just open the address in a browser. Everything after setup lives on /admin, linked from House → Server for the owner.

What the household gets

Shared bills, private money, one honest balance.

The household is jointly visible by design, and everything about your own money sits behind a boundary the shared side cannot read through.

The household

Both of you

Recurring bills — rent, energy, broadband, subscriptions — split equally, by percentage, or paid entirely by one person. For bills that vary, you enter what each one actually came to.

  • Who pays each provider, each person’s share, and who has paid.
  • One-off money lent between two people, all or part of it owed back.
  • A running balance with each person, part-payments, and live updates as things change.
  • Reminders before bills are due, scheduled on each phone.

Yours — private to you

You only

A private space nobody else in the household can see, including whether you use it. Only your share of the household bills crosses inwards; nothing is ever written back.

  • What’s left after bills, from your pay.
  • Bills that are yours alone, and an emergency fund.
  • A debt-payoff planner — snowball or avalanche, 0% offers, a debt-free date.
  • Reading a bank export (Monzo CSV and similar) on your device to find what you could cut.

The bit that’s different

Two reminders, two confirmations, one closed bill.

Most splitting apps only chase the money. The awkward part of a shared house is earlier: somebody has to read the meter or say what this month’s number is. KTL treats that as its own step with its own deadline.

Five days out · both of you file the details Readings, usage, this month’s amount. Each person ticks that they’ve shared theirs, so nobody is guessing on the day.
Two days out · whoever owes sends it The reminder carries the exact amount, the responsible bill payer, their account and the reference.
On arrival · the bill payer confirms Only their confirmation closes the line and clears it from the balance. Neither step closes on a notification being seen — each closes on a person tapping a confirmation.

Chase and confirm

Default

Both of you are prompted and both of you confirm. Best when money genuinely moves between you every month.

  • Details reminder five days out, money reminder two days out.
  • Anything unconfirmed gets one nudge after 24 hours.

Tracking only

No chasing

KTL becomes a shared ledger rather than a chaser, for couples who settle up their own way and just want the numbers to agree.

  • Costs, split and running balance still tracked in full.
  • Say you’ve paid and the line closes on the spot.

Away from home

Reaching it from outside your network

Cloudflare Tunnel

No open ports needed. Create a tunnel in Cloudflare Zero Trust, add a public hostname pointing at the service, then paste the token on the admin page.

  • Zero Trust → Networks → Tunnels → create a tunnel.
  • Add a public hostname (e.g. ktl.example.com) with service http://localhost:3000.
  • Paste the tunnel’s token under Remote access on the admin page.
  • Set the address to https://ktl.example.com.

Reverse proxy

Nginx Proxy Manager, SWAG, Caddy or Traefik works too: proxy your hostname to http://<server>:8095 with HTTPS.

  • Live updates use server-sent events — turn off response buffering on the proxy.
  • If the proxy is on another machine, turn on Trust a reverse proxy on the admin page so the server sees real client addresses (used for sign-in rate limits).

Day two

Running it

Backups and restore

Each night a consistent copy of everything, accounts included, goes into /data/backups. The last 14 are kept, and the time and number kept can be changed on the admin page. Backups can be downloaded, and restored, from there too. That folder is what your own backups should keep — copying /data/postgres while the server runs isn’t reliable.

From a terminal instead:

docker exec -it ktl ktl-admin restore /data/backups/<file>.dump --yes

It saves the current data first, and runs in a single transaction.

Updating and the terminal

To update, pull the latest code, rebuild the image and recreate the container; database changes apply on start. From a terminal, ktl-admin covers the rest:

docker exec -it ktl ktl-admin help

setup-code, status and users; reset-link and set-password (for when there’s no email server); backup, restore and import-json. Health lives at /healthz, reporting the database, sign-in and data API.

Settings, and where they live

Everything is on the setup and admin pages. You can also set any of these on the container, which locks that setting — the admin page then shows it as “set by the container”.

VariableWhat it does
KTL_SITE_URLThe address people open, e.g. https://ktl.example.com.
KTL_ALLOW_SIGNUPtrue to let anyone who reaches the server create an account.
KTL_SMTP_HOST, _PORT, _USER, _PASS, _SENDER, _SENDER_NAMEEmail, for password resets.
CLOUDFLARE_TUNNEL_TOKENRuns a Cloudflare Tunnel inside the container.
KTL_FCM_SERVICE_ACCOUNTA Firebase service-account key (JSON), for push.
KTL_TRUST_PROXYtrue behind a reverse proxy on another machine.
KTL_BACKUP_KEEP, KTL_BACKUP_HOURNightly backups to keep (14) and the hour to take them (3).
KTL_TIMEZONETime zone for the backup time. Defaults to Europe/London.
KTL_UPDATE_CHECKfalse stops the server checking GitHub for a newer KTL.
